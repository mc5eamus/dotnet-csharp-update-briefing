.NET 10 & C# 14 LTS

Everything today is generally available, supported until November 2028, and safe to put into production. The only real question is sequencing.

What you'll leave with
  • A concrete upgrade order for your own codebase
  • Working code for every feature that matters to you
  • An API and a data model that you migrate to .NET 11 tomorrow
Shaped by your survey

Weighted towards EF Core, ASP.NET Core and the .NET libraries. No MAUI, no Blazor, no F#/VB.NET.

Open by asking the room which .NET version they're on today. The answer changes how you pitch the rest of the day: a room still on .NET 8 or .NET 9 has roughly eight weeks of support left and needs an urgent plan, not a feature tour.

The cadence, and why it decides your upgrade plan

.NET ships every November, alternating between long-term and standard-term support. That alternation — not the feature list — is what drives most upgrade decisions.

ReleaseShippedTrackSupport endsWhere you stand
.NET 8Nov 2023LTS10 Nov 2026Maintenance — weeks left

STS is 24 months now, not 18 — and it changes the arithmetic

Microsoft extended STS support from 18 to 24 months, effective from .NET 9. STS releases now get 12 months past their successor, the same as LTS.

Two consequences most people have not caught up with:

  • .NET 9 did not expire in May 2026. It runs to 10 November 2026 — the very same day as .NET 8. If you assumed you were already unsupported, you are not.
  • .NET 8 and .NET 9 now die together, in about eight weeks. Whichever of the two you are on, the deadline is identical and it is close.
The practical reading

If you are on .NET 8 or .NET 9, you have until 10 November 2026, and .NET 10 is the obvious destination — it is GA, LTS and supported for three more years.

The interesting part is what this does to tomorrow's decision. .NET 10 LTS ends 14 November 2028. .NET 11 STS, shipping November 2026 with 24 months, ends around November 2028. Those are the same week. The old reflex of "take LTS because it is supported longer" no longer describes reality.

Worth being explicit: STS releases are not "beta" or lower quality. They carry the same production-support commitment. Since the 24-month change they carry very nearly the same window too.

Expect pushback here — plenty of people in the room will "know" that STS is 18 months, because it was until the .NET 9 announcement. The sources page links the announcement; it is worth showing if challenged. This correction sets up the Day 2 decision slide, so do not rush it.

Getting to .NET 10

Retargeting is usually a one-line change. The work is in what surfaces afterwards.

<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <!-- C# 14 is the default for net10.0; you do not need to set LangVersion. -->
</PropertyGroup>

A pragmatic order that keeps each step independently revertible:

  1. Retarget and build. Fix only what breaks compilation.
  2. Run your test suite before adopting a single new language feature. Keep the "did the runtime change break us?" question separate from "did our refactor break us?"
  3. Update packages — especially EF Core, which must match the major version.
  4. Then adopt C# 14 features, where they earn their place.
EF Core versions are not optional

EF Core 10 requires .NET 10. Mixing an EF Core 9 package into a net10.0 app usually works but leaves you without this release's query-translation fixes — and it silently blocks tomorrow's EF Core 11 migration lab. Upgrade the package with the TFM.

Tooling that helps

  • dotnet-upgrade-assistant — automates retargeting and flags API removals.
  • dotnet list package --outdated — the fastest way to find package drift.
  • dotnet list package --vulnerable --include-transitive — run this anyway; upgrades are a good moment to clear known CVEs.

File-based apps: C# without a project

.NET 10 lets you run a single .cs file directly. No .csproj, no obj/, no scaffolding.

dotnet run hello.cs

Dependencies and settings come from #: directives at the top of the file:

#:package Humanizer@2.14.1
#:property LangVersion=preview

using Humanizer;

var span = TimeSpan.FromMinutes(1234);
Console.WriteLine(span.Humanize(precision: 2));
Why this matters beyond demos

It removes the friction from the things people currently do badly: build scripts, one-off data fixes, reproducible bug reports. A colleague can now send you a single file that actually runs. When a file-based app outgrows itself, dotnet project convert turns it into a normal project.

Good live demo: write a five-line file in front of the room and run it. Then add a #:package directive and run it again to show restore happening transparently. It lands better than any slide about it.

Extension members C# 14

Extension methods have existed since C# 3. C# 14 generalises the idea: an extension block declares a receiver once, and can then contain properties, static members and operators — not just instance methods.

Before — C# 13
public static class SeqExtensions
{
    public static bool IsEmpty<T>(
        this IEnumerable<T> source)
        => !source.Any();

    // No way to express a property.
    // No way to express a static member
    // "on" IEnumerable<T>.
}
After — C# 14
public static class SeqExtensions
{
    extension<T>(IEnumerable<T> source)
    {
        // extension property
        public bool IsEmpty => !source.Any();

        public int CountFast => source is ICollection<T> c
            ? c.Count
            : source.Count();
    }

    extension<T>(IEnumerable<T>)
    {
        // static extension member
        public static IEnumerable<T> Empty => [];
    }
}

The receiver parameter is named once and shared by every member in the block, which is what makes properties possible — there is no this parameter to hang them on.

List<int> numbers = [1, 2, 3];

if (!numbers.IsEmpty)              // extension property
    Console.WriteLine(numbers.CountFast);

var nothing = IEnumerable<int>.Empty;   // static extension member
Note the second block has no parameter name

extension<T>(IEnumerable<T>) — type only, no identifier. That is how you declare static extension members: there is no instance to receive. Getting this wrong is the most common early mistake.

The honest framing: this is not "extension methods, but shorter". It changes what you can model. Anywhere your codebase has a FooHelpers or FooUtils static class, extension members probably express it better. Lab 01 is exactly that refactor.

Extension operators & compound assignment

Extension blocks can define user-defined operators — so you can add operator support to a type you don't own. The receiver is unnamed, because the operator declares its own parameters:

public static class VecExtensions
{
    extension(Vec)                      // <- no parameter name here
    {
        public static Vec operator +(Vec left, Pt right)
            => new(left.X + right.X, left.Y + right.Y);
    }
}
Naming the receiver is a compile error

Write extension(Vec left) around a static operator +(Vec left, …) and you get CS9290: 'left': a parameter, local variable, or local function cannot have the same name as an extension parameter. The operator's own parameters and the extension receiver share one scope. Use the unnamed form for operators.

Separately, C# 14 lets a type implement compound assignment operators directly, instead of synthesising them from the binary operator. Note the shape: an instance member, no left-hand parameter, returning void:

public struct Accumulator
{
    private long _total;

    // C# 13: only `operator +` — every `+=` allocated a new value.
    // C# 14: mutate in place.
    public void operator +=(long amount) => _total += amount;
}

The two features combine. A ref receiver gives you an in-place compound assignment operator for a type you don't own:

extension(ref Vec target)
{
    public void operator +=(Pt right)
    {
        target.X += right.X;
        target.Y += right.Y;
    }
}
When this actually pays

For large structs and accumulator types in hot loops, in-place compound assignment removes a copy per operation. For everything else the compiler-synthesised version is fine — this is a performance tool, not a style preference.

The field keyword C# 14

The single highest-frequency change in this release. You can now write property logic without declaring the backing field.

Before
private string _message = string.Empty;

public string Message
{
    get => _message;
    set => _message =
        value?.Trim() ?? string.Empty;
}
After
public string Message
{
    get;
    set => field =
        value?.Trim() ?? string.Empty;
}

Note that get; stays auto-implemented while set is custom. That combination was impossible before — declaring either accessor by hand forced you to declare both, plus the field.

Breaking change: existing symbols named field

Inside a property accessor, field now binds to the backing field rather than to any variable, parameter or member of that name. If you have a class member called field, disambiguate:

public string Name
{
    get => this.field;   // the member named 'field'
    set => @field = value; // also the member, via escaping
}

This is rare but silent when it happens, so grep for it before upgrading: \bfield\b inside property bodies.

Ask the room to guess how many backing fields exist in their main solution. The answer is usually "thousands", and most are pure ceremony. This feature alone often justifies the language upgrade to a sceptical tech lead.

Null-conditional assignment & smaller wins

Null-conditional assignment

?. now works on the left-hand side of an assignment:

// Before
if (customer is not null)
    customer.Order = GetCurrentOrder();

// C# 14
customer?.Order = GetCurrentOrder();
The right-hand side is not evaluated when the target is null

If customer is null, GetCurrentOrder() never runs. That is the behaviour you want, but it does mean the expression can have observably different side effects from the if form you replaced — worth a glance if the RHS mutates state.

Increment and decrement are not supported: customer?.Count++ does not compile.

Lambda parameter modifiers

You can now use ref, in, out and scoped without spelling out the parameter types:

// Before: types were mandatory once you needed a modifier.
TryParse<int> parse = (string text, out int result) => int.TryParse(text, out result);

// C# 14
TryParse<int> parse = (text, out result) => int.TryParse(text, out result);

nameof on unbound generics

string name = nameof(List<>);   // "List"

partial events and constructors

Partial members now extend to events and constructors, closing a long-standing gap for source generators: a generator can supply the implementation while your file declares the shape.

First-class span conversions

The compiler now recognises implicit conversions between arrays, Span<T> and ReadOnlySpan<T> as first-class conversions, which means overload resolution finally picks the span overload you expected.

void Process(ReadOnlySpan<int> values) { }

int[] numbers = [1, 2, 3];
Process(numbers);         // implicit array -> ReadOnlySpan<int>

Span<int> span = numbers;
Process(span);            // implicit Span<T> -> ReadOnlySpan<T>

Extension methods participate too, so numbers.SomeSpanExtension() now resolves without an explicit .AsSpan().

This can change which overload you bind to

If you have both Process(int[]) and Process(ReadOnlySpan<int>), recompiling under C# 14 may select a different one than before. Usually that is an improvement — fewer allocations — but if the two overloads behave differently, it is a silent behavioural change. Worth checking in any library that offers both shapes.

.NET 10 libraries .NET 10

This is the release where the base class library catches several problems that used to require specialist packages or defensive local conventions.

Crypto

Post-quantum algorithms are the headline: ML-KEM for key encapsulation, ML-DSA for signatures, SLH-DSA for stateless hash-based signatures and composite ML-DSA for migration paths.

JSON

System.Text.Json gains source-generated reference handling, duplicate-property rejection, stricter option defaults and better pipeline support.

Everyday APIs

Async ZIP APIs, better ordered dictionaries, numeric-aware string ordering, WebSocketStream and diagnostics improvements round out the module.

The theme is defensive modernisation

The most valuable changes here are not syntax. They remove places where teams have historically relied on "we always remember to do this safely" conventions.

Ask which topic brought people to this module: crypto, JSON hardening or "what do we get for free by retargeting?" Use that answer to decide how much time to spend on the grab-bag slide. PQC and JSON deserve the time even if only one person raises a hand.

Post-quantum crypto is now an application concern

PQC matters before quantum computers are practical at scale because of harvest now, decrypt later: an attacker can store encrypted traffic today and wait for cryptanalysis that makes old key exchange unsafe.

APIStandardUse it forTeaching point
MLKemFIPS 203Key encapsulationStable; key formats experimental
MLDsaFIPS 204Digital signaturesStable; key formats experimental
SlhDsaFIPS 205Stateless hash signaturesSupport varies
CompositeMLDsaComposite migrationHybrid-style signaturesExperimental warning
This is not "replace TLS tomorrow"

The practical move is inventory and controlled adoption: know where long-lived secrets exist, gate algorithm use at runtime, and avoid hard-coding assumptions about platform support.

Keep this calm. The room needs to understand why the topic matters without turning the workshop into a crypto scare story. For most application teams the first action is capability detection and migration planning, not rewriting every protocol.

The PQC APIs deliberately do not look like RSA

The new types do not derive from AsymmetricAlgorithm. They use static generate and import factory methods, and every real application must gate on IsSupported.

using System.Security.Cryptography;

if (!MLKem.IsSupported)
{
    throw new PlatformNotSupportedException("ML-KEM is not available here.");
}

// Recipient generates a key pair and publishes the encapsulation (public) key.
using MLKem recipient = MLKem.GenerateKey(MLKemAlgorithm.MLKem768);
byte[] publicKey = recipient.ExportEncapsulationKey();

// Sender uses it to agree a shared secret and produce a ciphertext.
using MLKem sender = MLKem.ImportEncapsulationKey(MLKemAlgorithm.MLKem768, publicKey);
sender.Encapsulate(out byte[] ciphertext, out byte[] senderSecret);

// Recipient recovers the same secret from the ciphertext alone.
byte[] recipientSecret = recipient.Decapsulate(ciphertext);
// senderSecret and recipientSecret are now identical.

Note the shape: there is no Encrypt/Decrypt pair. ML-KEM is a key encapsulation mechanism — it agrees a symmetric secret, which you then use with AES. Signing is a separate type:

using MLDsa signer = MLDsa.GenerateKey(MLDsaAlgorithm.MLDsa65);

byte[] data = Encoding.UTF8.GetBytes("invoice-4471");
byte[] signature = signer.SignData(data);          // 3309 bytes for ML-DSA-65

bool ok = signer.VerifyData(data, signature);

// Verification only needs the public key. Note the ML-DSA-specific export:
// the *standard* SPKI/PKCS#8 formats are still experimental here. See below.
byte[] publicKey = signer.ExportMLDsaPublicKey();
using MLDsa verifier = MLDsa.ImportMLDsaPublicKey(MLDsaAlgorithm.MLDsa65, publicKey);
bool alsoOk = verifier.VerifyData(data, signature);
Why no AsymmetricAlgorithm base?

Key encapsulation and modern PQC signatures do not map cleanly onto the old encrypt/decrypt/sign/verify base-class shape. The explicit APIs make misuse harder.

What code must do
  • Check IsSupported before offering the algorithm.
  • Expect OpenSSL 3.5+ or Windows CNG with PQC support.
  • Suppress SYSLIB5006 around key serialisation and the experimental algorithms.
The real experimental boundary is per-member, not per-type

The usual summary — "ML-KEM and ML-DSA are stable, SLH-DSA is not" — is only half the story, and the half it misses is the half that will stop your build. We enumerated ExperimentalAttribute by reflection on .NET 10.0.12:

TypeType-levelStable membersExperimental members
MLKemstable1214
MLDsastable1218
SlhDsaexperimentalwhole type
CompositeMLDsaexperimentalwhole type

The split inside MLKem and MLDsa is completely consistent:

  • Stable — the cryptography itself, plus the algorithm-specific raw key formats: GenerateKey, SignData, VerifyData, Encapsulate, Decapsulate, ExportMLDsaPublicKey, ImportMLKemEncapsulationKey, and friends.
  • Experimental — every standard key-interchange format: ExportSubjectPublicKeyInfo, ImportSubjectPublicKeyInfo, all the Pkcs8 variants, and everything ...Pem.

So: you can do post-quantum crypto today, but you cannot yet persist or interchange the keys without opting in to an unstable API. For a migration project that is the single most important fact on this slide — key storage and distribution is exactly where you were going to integrate.

SYSLIB5006 is an error, not a warning

It stops the build outright, so the suppression has to be deliberate. Keep it narrow — wrap the serialisation call, not the file:

#pragma warning disable SYSLIB5006   // Standard key formats are still evaluation-only.
byte[] spki = signer.ExportSubjectPublicKeyInfo();
using MLDsa verifier = MLDsa.ImportSubjectPublicKeyInfo(spki);
#pragma warning restore SYSLIB5006

The workshop machine is current Windows 11 25H2 running .NET 10. Two algorithms are available through the platform provider. One is not:

MLKem.IsSupported          : True
MLDsa.IsSupported          : True
SlhDsa.IsSupported         : False     <-- not available via Windows CNG on this build
CompositeMLDsa.IsSupported : True

ML-KEM-768   public key 1184 bytes, ciphertext 1088 bytes, shared secret 32 bytes, match=True
ML-DSA-65    signature 3309 bytes, verify=True, tampered=False
Look at those sizes before you design a protocol

A 3309-byte signature is roughly 13× an RSA-2048 signature, and the ML-KEM public key is 1184 bytes. That is the real cost of post-quantum security, and it lands on anything with a size budget — certificates, tokens, QR codes, embedded payloads, TLS handshakes. Measure before you commit.

IsSupported changes the control flow today

This is not a future portability nicety. On this machine ML-KEM and ML-DSA work, while SLH-DSA does not. Lab 02 is built around the two working paths and uses SLH-DSA as the visible reason to gate.

Do not invent method names live if you cannot remember the exact overloads. The lab gives attendees compilable code. Run the support probe live if the room is interested: different attendee results are a feature of the demo, not a failure.

System.Text.Json: less trust in input

.NET 10 continues the shift from "fast serializer" to "safe boundary component". The most important change for service teams is duplicate-property rejection.

The attack shape
{
  "role": "user",
  "role": "admin"
}
The defensive posture
var options = new JsonSerializerOptions
{
    AllowDuplicateProperties = false,
    RespectNullableAnnotations = true,
    RespectRequiredConstructorParameters = true
};

Duplicate properties are a real security hardening win because different parsers, gateways, loggers and application code may disagree about which value "wins". That parser differential is exactly what JSON injection attacks exploit.

  • ReferenceHandler can now be set from JsonSourceGenerationOptions.
  • Strict serialization options make missing required data and nullable mismatches fail earlier.
  • PipeReader support reduces copying when JSON arrives from pipelines.

Ask whether their API gateway, body logger and application deserializer are the same parser. They usually are not. That is the point: duplicate rejection belongs at the boundary before business logic has to reason about ambiguous input.

The smaller library changes you will actually use

More crypto hygiene
  • AES KeyWrap with Padding, matching RFC 5649.
  • PKCS#12/PFX export algorithm control.
  • Certificate lookup by non-SHA-1 thumbprints.
  • PEM discovery over ASCII and UTF-8 data.
Runtime-library polish
  • Async ZIP APIs and ZIP performance/memory improvements.
  • OrderedDictionary<K,V> adds TryAdd and TryGetValue.
  • Numeric-aware string ordering for "file2" before "file10" style sorting.
  • WebSocketStream for stream-shaped WebSocket handling.

Diagnostics also move forward: telemetry schema URLs, out-of-process Activity events and links, and rate-limit sampling are all aimed at making production traces easier to interpret rather than merely more verbose.

Do not let this become a catalogue reading. Pick one example that matches the room: archives for back-office systems, certificate lookup for platform teams, or numeric sort for anyone who has shipped "item10 before item2" bugs.

OpenAPI 3.1 is now the default ASP.NET Core 10

This is the ASP.NET Core 10 change most likely to show up in customer tooling, because it changes the document your generators and gateways consume.

Breaking change: nullable schema shape

OpenAPI 3.1 aligns with JSON Schema 2020-12. Nullable values are represented as type arrays instead of the OpenAPI 3.0 nullable extension.

OpenAPI 3.0
{
  "type": "string",
  "nullable": true
}
OpenAPI 3.1
{
  "type": ["string", "null"]
}

The underlying OpenAPI stack also moves to Microsoft.OpenApi 2.0.0. Treat the generated document as a compatibility surface and test it, not just the HTTP endpoint.

It says 3.1.1, not 3.1.0

Verified against the document Lab 03 actually generates: the emitted value is "openapi": "3.1.1". Any contract test, gateway policy or client generator that string-matches an exact version rather than the 3.1.x family will trip over this.

It gets worse on Day 2. We measured the same probe on .NET 11 RC 1: the default becomes 3.2.0, and pinning back to “3.1” yields 3.1.2 — not the 3.1.1 you have today. So an exact-match assertion breaks on upgrade even if you deliberately pin the version back.

Ask who has client generation in CI. Those teams need to run generation after retargeting and compare the output. The server can be perfectly correct while downstream tooling still needs an OpenAPI 3.1 update.

The 3.1.1 detail reliably gets a reaction from anyone who maintains contract tests. It is also the setup for Lab 08, where they migrate this exact app and watch the string move again.

OpenAPI output is easier to make useful

ASP.NET Core 10 improves the document pipeline around the places teams actually touch: format, endpoint comments and descriptions.

Serve JSON and YAML
app.MapOpenApi();
app.MapOpenApi("/openapi/{documentName}.yaml");
Let XML comments flow through
app.MapGet("/orders/{id}", GetOrder)
   .WithName("GetOrder");

/// <summary>
/// Gets an order by identifier.
/// </summary>
/// <remarks>Returns 404 when the order does not exist.</remarks>
static IResult GetOrder(int id)
    => TypedResults.NotFound();
{
  "summary": "Gets an order by identifier.",
  "description": "Returns 404 when the order does not exist."
}

Response descriptions can also be supplied through ProducesResponseType, which makes status-code meaning visible to generated clients and API reviewers.

The useful demo is opening the generated YAML next to the endpoint code. XML comments tend to be dismissed as ceremony until people see them appear in the contract their consumers actually read.

The OpenAPI pipeline is now programmable

You can retrieve generated documents from DI with IOpenApiDocumentProvider, customize individual operations, and use schema generation inside transformers.

builder.Services.AddOpenApi(options =>
{
    options.AddOperationTransformer((operation, context, cancellationToken) =>
    {
        if (context.Description.ActionDescriptor.EndpointMetadata
            .OfType<RequiresTenantAttribute>().Any())
        {
            operation.Parameters.Add(/* tenant header parameter */);
        }

        return Task.CompletedTask;
    });
});
Why this matters

Most production APIs have contract rules that are not obvious from a delegate signature: tenant headers, correlation identifiers, feature flags or gateway-only metadata. Operation transformers are where those rules belong.

Keep the code schematic. The exact parameter object is less important than the fact that this now belongs in the supported OpenAPI generation pipeline rather than a post-processing script that nobody remembers to run.

Validation moved into the shared stack

Minimal API validation is no longer something every team has to hand-roll. The validation APIs live in Microsoft.Extensions.Validation and integrate with IProblemDetailsService.

builder.Services.AddProblemDetails();
builder.Services.AddValidation();

app.MapPost("/orders", (CreateOrderRequest request) =>
{
    return TypedResults.Created($"/orders/{request.Id}", request);
});

public sealed record CreateOrderRequest(
    Guid Id,
    [property: Required] string CustomerId,
    [property: Range(1, 999)] int Quantity);

The practical change is consistency. Invalid DTOs can now produce the same problem-details shape whether the endpoint is MVC or Minimal APIs.

Package boundaries changed

If you had preview validation APIs wired directly into ASP.NET Core, expect namespace and package cleanup during the .NET 10 migration. The capability moved to Microsoft.Extensions.Validation.

Ask how many Minimal API endpoints in the room validate by calling a local helper at the top of every delegate. This feature is a good moment to replace that pattern with framework behaviour and one error contract.

Streaming and patching move forward

Server-Sent Events

app.MapGet("/events", () =>
{
    async IAsyncEnumerable<SseItem<string>> Stream()
    {
        while (true)
        {
            yield return new SseItem<string>($"tick {DateTimeOffset.UtcNow}");
            await Task.Delay(TimeSpan.FromSeconds(1));
        }
    }

    return TypedResults.ServerSentEvents(Stream());
});

JSON Patch without Newtonsoft.Json

ASP.NET Core 10 adds a new JSON Patch implementation built on System.Text.Json. That removes a common Newtonsoft dependency, but it is not a byte-for-byte behavioural clone, so test existing patch documents during migration.

  • Auth/authz and Identity add metrics you can feed into existing telemetry.
  • Cookie login no longer redirects for API endpoints; APIs get API-shaped responses.
  • Memory pool eviction reduces long-lived memory retention under changing workloads.
  • .localhost is treated as a local development top-level domain.

SSE is a good live demo because the browser shows it immediately. JSON Patch is the migration warning: if a public client sends patch documents today, include those documents in the upgrade test set rather than assuming equivalent behaviour.

Complex types are the EF Core 10 headline EF Core 10

For value objects, complex types are now the model you should reach for first. Owned entity types still exist, but they were overloaded for too many jobs.

public sealed class Customer
{
    public int Id { get; set; }
    public required Address BillingAddress { get; set; }
}

public readonly record struct Address(
    string Line1,
    string City,
    string Country);

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Customer>()
        .ComplexProperty(c => c.BillingAddress);
}
What EF Core 10 adds
  • Table splitting for complex type properties.
  • JSON mapping for complex values.
  • Struct support, which fits immutable value objects.
Rule of thumb

Use complex types when the value has no identity of its own. Use an owned entity type only when you need entity-like behaviour that a value object should not have.

This is the highest-interest module. Spend time on the modelling guidance, not just the API. Many teams used owned types because they had no better option; EF Core 10 gives them a cleaner vocabulary for value objects.

Named query filters solve the "one giant filter" problem

EF Core has long supported global query filters. EF Core 10 lets you name multiple filters on the same entity and disable one without disabling the rest.

modelBuilder.Entity<Order>()
    .HasQueryFilter("SoftDelete", o => !o.IsDeleted)
    .HasQueryFilter("Tenant", o => o.TenantId == tenantId);

var withDeleted = await db.Orders
    .IgnoreQueryFilters(["SoftDelete"])
    .ToListAsync();
The real win is operational

Support tooling can include soft-deleted rows without accidentally bypassing tenant isolation. Before named filters, teams often had to combine unrelated rules into one expression and then choose between all filters or none.

Ask who has soft delete and multi-tenancy in the same model. This feature is aimed directly at that pain. Emphasise that disabling a filter by name should be rare and auditable, not sprinkled through application queries.

JSON columns and bulk updates get more practical

EF Core 10 improves relational JSON column support, including ExecuteUpdate for JSON columns. It also makes bulk update code easier to read.

Before
await db.Orders.ExecuteUpdateAsync(setters =>
    setters.SetProperty(
        o => o.Status,
        o => OrderStatus.Archived));
EF Core 10
await db.Orders.ExecuteUpdateAsync(setters =>
{
    setters.SetProperty(
        o => o.Status,
        o => OrderStatus.Archived);
});

The regular statement lambda matters because real updates rarely fit nicely on one line. You can keep the update readable without breaking the server-side bulk operation shape.

Provider reality still applies

JSON support is relational-provider specific. In this workshop the lab uses SQLite, so JSON-column walkthroughs are discussed as capability and migration planning, not as a hands-on provider feature.

If attendees ask whether this replaces tracked updates, answer no. It is for set-based updates that should happen in the database. The readability improvement just makes that pattern less hostile in real code.

Vector search is here, but not in today's SQLite lab

EF Core 10 includes vector search support for Azure SQL and SQL Server. That is important for search and AI-adjacent workloads, but it is provider-specific.

Walkthrough, not runnable lab code

The Day 1 EF lab uses SQLite so everyone can run it locally. Treat vector search as a provider walkthrough today: shape the model, discuss indexing and query intent, but do not expect the lab database to execute Azure SQL vector operations.

Query operators
  • LeftJoin and RightJoin reduce awkward group-join patterns.
  • Parameterized collections translate better.
  • Split-query ordering is more consistent.
Other provider work
  • Custom default constraint names.
  • Cosmos full-text search leaves preview.

Be clear that "EF supports vector search" does not mean "every provider supports vector search". That distinction prevents frustration in the lab and sets up the deeper SQL Server vector discussion tomorrow.

EF Core 10 makes unsafe patterns harder to miss

Two security changes are worth calling out because they reduce real incident risk without asking every developer to remember another checklist item.

Logs leak less by default

Inlined constants are redacted from EF logs by default. That helps prevent customer identifiers, tokens or query literals from ending up in central logging systems.

Raw SQL gets a warning

EF warns when it sees string concatenation with raw-SQL APIs. It is a direct guardrail against accidental SQL injection in code review-resistant paths.

// Suspicious: user input is being concatenated into raw SQL.
var sql = "SELECT * FROM Orders WHERE CustomerId = '" + customerId + "'";
await db.Orders.FromSqlRaw(sql).ToListAsync();
Frame this as production hygiene

These are not flashy features, but they matter in audits: fewer secrets in logs, and earlier feedback when raw SQL drifts away from parameterization.

Do not turn this into a SQL injection lecture. The point is that EF Core 10 gives teams better defaults and warnings in exactly the places where mistakes usually survive code review.
